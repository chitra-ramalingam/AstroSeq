## Root Cause Investigated

Issue observed:

- Rows with missing `P` (`no_period_rows`) appeared in summary output.
- Best subset was biased by period distribution.

Root cause for null `P`:

- `P` is produced from `infer_periods_from_events(events_df)` and later candidate filtering/validation flow.
- For some EPICs, period inference produced no usable candidates (`reason=no_cluster_periods`), so summary rows existed with null `P`.
- These rows entered raw summary and needed explicit quarantine/drop before downstream scoring/plots.

Typical no-cluster failure categories now tracked:

- `insufficient_events`
- `empty_histogram`
- `candidate_filter_rejection`

## Implemented Fixes

### 1) Quarantine + fail-fast for null/invalid `P`

Implemented in `K2ShortlistPeriodRunner`:

- Hard validation of `P` before downstream:
  - null/missing
  - non-positive
  - below min period
  - above configured cap
- Invalid rows are dropped from downstream and written to quarantine CSV.
- Fail-fast threshold retained:
  - default `NULL_P_RATE_MAX = 0.001` (0.1%)
  - raises with top 20 EPIC IDs for unexpected null-`P` rows.
- Exemption handling improved:
  - expected `no_cluster_periods` can be exempted
  - fallback infers `source_reason` from `missing_upstream_source` when `source_reason` is blank.

Quarantine columns now include:

- `epic_id`
- `query`
- `reason`
- `missing_upstream_source`
- `source_reason`
- `failure_category`
- `failure_detail`
- `n_events_raw`
- `n_events_after_filters`
- `infer_max_period_days`
- `infer_min_hits`
- `infer_tol_frac`
- `min_cluster_count`
- `period_cap_days`
- `P`

### 2) Canonical summary outputs (no accidental double counting)

Explicit summary outputs created:

- `period_shortlist_summary_unique_epicP.csv` (deduped by `(epic, P)`)
- `period_shortlist_summary_validated_only.csv` (`reason=validated`, then deduped)

Plotting and aggregate counts use canonicalized summary instead of duplicated raw reason rows.

### 3) Best debiasing by period bins

Stratified Best selection implemented with bins:

- `(1, 5]`
- `(5, 10]`
- `(10, 15]`
- `(15, 20]`

Configurable quota mode added (`BEST_SELECTION_BIN_MODE`):

- `match_summary_distribution`: per-bin quotas proportional to Summary distribution.
- `equal_per_bin`: per-bin quotas distributed evenly.

Diagnostics now include:

- `best_bin_mode`
- `summary_bin_counts`
- `best_bin_quotas`
- `best_bin_achieved`

### 4) Period cap is first-class and consistent

Cap setting:

- `PERIOD_CAP_DAYS` in config (default `20.0`)

Used consistently in:

- period filtering/validation
- histogram bins
- diagnostics
- plot annotation (`cap P <= ... d`)

### 5) Inference-failure diagnostics for `no_cluster_periods`

For EPICs where inference fails:

- detailed payload logged with event counts, inference params, and categorized failure reason
- payload stored in-memory and merged into quarantine rows for those EPICs.

## 25K Scale-Validation Plan

Goal:

- estimate whether quality-gated detector gains and downstream behavior generalize beyond the cached-failed slice
- keep compute much smaller than a full 25K rerun
- preserve enough structure to detect whether wins are confined to the failure-enriched region

### Recommended design

Use a paired, weighted stratified sample from the full K2 pool. Run both detector modes on the same sampled EPICs, then run downstream on the sample without a random `period_stage` cap.

Recommended sample size:

- preferred: `800` EPICs
- minimum credible fallback: `600` EPICs if compute is tight

Recommended `n = 800` allocation:

- unusable with detector/triage error: `111`
- unusable due to explicit quality gate: `52`
- usable with `n_events = 0`: `192`
- usable with `n_events = 1`: `162`
- usable with `n_events >= 2` and `n_periods_validated = 0`: `229`
- usable with `n_periods_validated >= 1`: `54`

Within each major stratum:

- preserve campaign balance if campaign metadata is available in the 25K manifest
- otherwise split by `triage_step_score` tertile
- in unusable strata, preserve major `triage_why_not_usable` buckets

### Metrics to report

All top-line metrics should be weighted back to the 25K population using stratum weights `N_h / n_h`.

Detector:

- detector winner rate: share where `quality_gated_n_events > default_n_events`
- detector improvement rate by stratum
- count with shape-score improvement
- count with depth-SNR improvement

Downstream:

- downstream conversion rate among detector winners
- shortlist volume: `best_per_1000`, `quarantine_per_1000`, and `quarantine_to_best_ratio`
- weighted counts of detector winners, downstream best rows, and quarantined winners
- dominant downstream failure reasons using:
  - `failure_category`
  - `shortlist_rejection_reason`
  - `terminal_reason`
  - actionable post-rescue buckets (`true insufficient signal`, `histogram handling`, `cluster/period policy`)

Diagnostics:

- report all metrics overall and by stratum
- include 95% confidence intervals with finite-population correction
- check whether quality-gated wins appear outside the cached-failed-like strata

### Go / no-go criteria

Go:

- weighted downstream conversion among detector winners is at least `0.60`
- weighted downstream conversion is not worse than the cached-failed baseline by more than about `10-12` percentage points from `0.724324`
- at least `15` observed winners, or at least `20%` of weighted winners, come from `triage_usable = True` strata
- `insufficient_events + empty_histogram` remain at least `75%` of quarantined-winner failures
- no new single downstream failure bucket exceeds `15%`
- shortlist load remains operationally acceptable and there is no meaningful pattern of quality-gated turning default downstream successes into failures

No-go / hold:

- downstream conversion collapses materially below the thresholds above
- wins are confined almost entirely to cached-failed-like / unusable strata
- a new dominant failure mode appears
- shortlist load inflates sharply relative to best output

### Assumptions and limitations

- The cached-failed broader study is a lever-discovery study, not a representative population estimate.
- The full-pool sample design assumes the same default-run metadata used above is available when drawing the 25K sample.
- If the first `400` sampled EPICs produce very few winners, the sample should be expanded toward `1000` to stabilize the downstream-conversion estimate.
- This is a planning/report recommendation only; no implementation was required for the plan itself.



------------
Conclusion

Lowering MIN_CLUSTER_COUNT from 3 to 2 is now established as a validated-science-yield lever in k2_shortlist_period, not only a candidate-stage recovery lever. In the validation-capable 2000-EPIC comparison, MCC=3 produced 282 validated unique EPICs and MCC=2 produced 514, rescuing 232 validated EPICs (+82.3%). However, the rescued validated set remains materially weaker than the MCC=3 baseline: it shifts toward shorter periods, has far fewer post-filter events, and shows weaker hit-rate metrics overall.

Policy:

- MIN_CLUSTER_COUNT=3 remains the conservative, precision-first default.
- MIN_CLUSTER_COUNT=2 is a supported high-recall mode with explicit cluster_count == 2 guardrails and manual review.
- Any validated row with cluster_count == 2 must retain explicit review/guardrail handling.
- This does not justify changing the default: the quality tradeoff remains real even though the validated yield gain is now proven.

Next steps

Keep MCC configurable.
Preserve rescued-review exports.
Add or keep guardrails for cluster_count == 2.
Revisit the default only if a future validation-capable run shows acceptable quality for rescued candidates.

PR Summary

This change formalizes `k2_shortlist_period` operating modes after the MCC rescue study and aligns code, reporting, and docs with the validated results.

What changed:

- `MIN_CLUSTER_COUNT=3` remains the default.
- `MIN_CLUSTER_COUNT` remains configurable via CLI.
- Mode language is now explicit:
  - `MCC=3` = conservative, precision-first default
  - `MCC=2` = supported high-recall mode
- `cluster_count == 2` handling is preserved through manual-review flags, guardrail thresholds, and rescued-review / comparison exports.
- Comparison reporting continues to separate candidate-stage rescue, validated-stage rescue, and rescued-set quality.

Why:

Separating whiteness improved bookkeeping, but whiteness was not the main shortlist recovery lever. The dominant recovery lever was lowering `MIN_CLUSTER_COUNT` from 3 to 2. That increases recovery, but it also preferentially admits weaker candidates, so the codebase now distinguishes a precision-first default from a higher-recall mode with explicit review and guardrails.

Validated 2000-EPIC result:

In a validation-capable 2000-EPIC comparison:

- `MCC=3` produced `282` validated unique EPICs.
- `MCC=2` produced `514` validated unique EPICs.
- `MCC=2` rescued `232` validated EPICs (`+82.3%`).

This establishes `MCC=2` as a validated-science-yield lever at scale, not just a candidate-stage yield lever. However, the rescued validated set remains materially weaker than the `MCC=3` baseline: it trends toward shorter periods, fewer post-filter events, and weaker hit-rate metrics. Guardrails remain active, and no validated `cluster_count == 2` rows that failed guardrails remained in the best table.

Operating modes:

- `MCC=3` is the conservative, precision-first default. Use this when shortlist quality is the priority.
- `MCC=2` is a supported high-recall mode. Use this when recovery is the priority, but keep `cluster_count == 2` guardrails and manual review enabled.

This closes the current tuning phase: `MCC=2` is supported, but it is not promoted to the default.
